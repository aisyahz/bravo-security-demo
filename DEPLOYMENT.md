# IWHost staging deployment — instructions only

No hosting access or deployment has been performed. Do not upload this project into the live WordPress document root and do not overwrite WordPress files, database or .htaccess.

1. In IWHost cPanel, create a separate staging subdomain with its own empty document root. Confirm the resolved directory is separate from the live WordPress root. Enable its SSL certificate. Password-protect staging through cPanel Directory Privacy and add a staging-only `X-Robots-Tag: noindex, nofollow` response header through the host-supported configuration. Do not submit staging to search engines.
2. Select a currently supported PHP version (local validation used 8.4.27). Confirm sessions, JSON, random_bytes, flock and outbound mail are available. Disable display_errors in hosting settings; keep private error logging enabled.
3. Upload only `dist/Bravo-Production.zip`, extract into that empty staging directory, then remove the uploaded ZIP. Confirm index.html, contact.php, includes and assets sit directly in the staging document root. Use normal file permissions (typically files 644 / directories 755); do not use 777. Do not upload bravo-latest.zip, the repository, tests, .local-tools, tools or development dependencies.
4. The package includes a small Apache .htaccess for DirectoryIndex, response headers and compression, plus an includes deny rule. Check that IWHost permits these directives; if a 500 error occurs, inspect its error log and have the host adjust the staging configuration. Never copy this .htaccess over WordPress's.
5. Verify the throttle directory resolves outside ALL public document roots and is private and writable by PHP. Prefer a private account directory configured through BRAVO_RATE_LIMIT_DIR in the PHP environment. Verify persistence, file locking and any open_basedir restrictions. Do not place rate state under assets or includes. Check that REMOTE_ADDR represents the visitor, especially behind a CDN/proxy; only the host should restore trusted proxy addresses.
6. With client authorisation, submit a clearly labelled staging enquiry to the configured general.bravonetwork@gmail.com recipient. Sender is website@bravosecuritynetwork.com.my; confirm the host authorises that sender and its domain mail authentication. Verify actual receipt, spam folder placement, subject/body and Reply-To. A green browser message only proves mail transport acceptance. Check failure handling using a host-approved staging mail rejection; restore working configuration afterward.
7. Test a fresh-session submission, invalid phone, missing/invalid CSRF, honeypot and repeat-attempt throttling. Confirm no mail is sent on rejection. Verify no PHP source, private rate data or directory listing is exposed. PHP contact responses must be no-store. Test HTTPS session cookie flags and all security/compression headers on Apache; the local PHP server cannot test .htaccess.
8. Check all four pages, twelve service selections, links, mobile menu, lightbox, keyboard focus, reduced motion and the eight widths (320, 375, 390, 430, 768, 1024, 1440, 1920). Check actual iOS Safari and Android Chrome touch/rotation, slow-network image loading, Google Maps, WhatsApp app handoff, phone and email actions.
9. Obtain the approvals listed in CLIENT-APPROVALS.md. Verify canonical / OG URLs and sitemap.xml against the eventual public location. Keep staging password-protected and excluded from indexing. Any later production migration, removal of staging restrictions or replacement of WordPress needs a separate authorised plan and backup; it is outside this task.

Rollback on staging: restore only a known staging backup or remove the newly uploaded allowlisted files from the verified staging root. Never apply a recursive cleanup to the parent hosting account or live WordPress directory.
